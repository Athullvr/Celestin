### Row-lock-specific cases if that alternative is selected

1. Verify the project runtime login can acquire the selected row lock on every required RLS-visible authorization relation with only approved privileges; verify it cannot lock another workspace's records.
2. Enumerate and lock each authoritative row: principal/service identity, workspace, project, project-login mapping, workspace membership where relevant, and the specific human/service project grant. Prove a missing/revoked row denies and cannot be bypassed by a stale in-memory `ResolvedProjectScope`.
3. Run concurrent multi-row revocation/identity transitions under opposing orders. Assert no deadlock, or define a bounded deadlock retry that redoes all authorization before work. Avoid planner-dependent row order.
4. Verify no advisory wrapper, trigger, migration path, or provisioning function remains a required dependency. A public arbitrary advisory call must not block ordinary request/revocation/migration operations in the dedicated Celestin database.
5. Verify the migration coordinator works on an already initialized version-9 database and separately define safe single-runner bootstrap for a fresh database without a ledger.

## Test execution boundary

The source-level tests listed above may run without PostgreSQL when selected directly and without the `--run-postgres-integration` option. The guarded `tests/postgres/test_live_authorization.py` and other live modules must not be included in an offline run unless the test configuration is inspected and the live opt-in remains absent. A skipped live test is not a pass. Live testing is a separate, explicitly authorized milestone after the database target and role identities have been positively verified.

For row-lock design, add offline tests only for actual SQL construction, required lock rows/order, and fail-closed behavior once the implementation contract is approved. Do not use fakes as evidence of PostgreSQL row-lock semantics.
