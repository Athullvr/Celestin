# Hosted tenancy schema spike

**Status:** Draft for team review. This is not wired into the application and is not a production migration. The local SQLite schema, MCP tools, and runtime configuration are unchanged.

## Assumptions to approve

- Workspace members do not automatically read every project. Project access is represented by explicit grants. Workspace roles (`owner`, `admin`, `member`) govern workspace administration only; authorization code must define what each role can administer.
- Human principals are identified by `(issuer, subject)`. Email is not an identity key.
- Project grants carry independent `can_read` and `can_write` flags; write implies read.
- IDs are generated by the application. This avoids a database extension requirement and lets the migration preserve existing SQLite integer record IDs.
- This draft targets PostgreSQL 15 or later for the column-list form of `ON DELETE SET NULL`, which preserves the project ID while clearing a deleted source reference.

## Initial hosted schema sketch

The adjacent SQL file is an empty-database schema spike for membership, projects, messages, and decisions. It demonstrates two important invariants: a user grant must belong to the same workspace as the user, and a decision's source message must belong to the same project. It does not migrate any local database contents.

| Hosted entity | Existing local counterpart / migration note |
|---|---|
| `celestin_users` | No local user table; create only from the trusted identity provider subject. |
| `celestin_workspaces` | New organization boundary. Workspace ownership must be provisioned by an approved administrator flow. |
| `celestin_workspace_memberships` | New membership state/role. Suspended and invited members are not authorization grants. |
| `celestin_projects` | Maps each legacy text `project` key to a workspace-scoped UUID and slug. A human must approve the mapping; project names alone cannot choose the workspace. |
| `celestin_project_memberships` | Explicit per-user access. Review whether the team wants workspace-wide inherited project access instead. |
| `celestin_service_identities` / `celestin_service_project_grants` | Constrained non-human principals; credentials are not stored in this schema. Credential issuance/revocation remains an identity-provider or secret-management concern. |
| `chat_messages` | Existing messages move from text project keys to `project_id`; preserve `conversation_id`, role, content, and timestamp. |
| `project_memory` | Existing decisions move to `project_id`; preserve key, value, status, and source link. Add `created_at`; legacy backfill may only approximate it using `updated_at`. |

Research/document content is intentionally not duplicated here. The existing PageIndex `documents` and `sections` store is a separate SQLite sidecar. A hosted migration should first decide whether its source documents become authoritative `research_records` or stay an entirely rebuildable index over separately stored content.

## Local-to-hosted migration outline

1. Provision workspace UUIDs and user memberships from the selected identity provider; do not infer them from local records.
2. For each local SQLite database, prepare an explicit mapping from each exact legacy project string to one workspace/project UUID. Fail the migration on missing or duplicate ambiguous mappings.
3. Load workspace/project rows, then messages, then decisions, preserving timestamps and IDs where they do not collide. IDs may be preserved per project because hosted constraints scope the source link to a project; application response IDs remain opaque.
4. Validate row counts, status/role constraints, and source-message links. Rebuild FTS/vector/document indexes from authoritative migrated records rather than importing local sidecars as truth.
5. Keep the original SQLite file backed up and read-only until a verified restore and cutover. This spike has no import, rollback, or production deployment code.

## Verification status and blocker

The composite foreign key and grants still need to be exercised against a disposable PostgreSQL 15+ server. This environment has neither `psql`/`initdb` nor the optional `psycopg` driver. Docker is installed, but its Linux engine is not running (`docker info` cannot connect to `dockerDesktopLinuxEngine`). No PostgreSQL syntax or database behavior is claimed as tested. The next verification step is to run the schema file against a disposable PostgreSQL instance, then test same-project references, cross-project references, membership workspace consistency, and delete-to-null provenance behavior.

## Team decisions before treating this as a migration

1. Confirm explicit per-project grants versus inherited workspace access.
2. Confirm who provisions workspaces and project mappings, and who may grant/revoke access.
3. Confirm service identity ownership and whether machine identities may write.
4. Confirm whether local decisions gain an authoritative `created_at` during import or preserve the approximation.
5. Confirm document/research source-of-truth and deletion/retention behavior.
