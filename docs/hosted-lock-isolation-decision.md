# Hosted PostgreSQL Lock Isolation — Decision Record

**Status: design proposal; no new security architecture is accepted by this document. No migration 0010 has been created or applied.** The hosted tenant-isolation gate remains closed until the decisions and evidence below are complete.

This document supplements [the advisory-lock privilege-boundary proposal](postgres-advisory-lock-privilege-boundary-proposal.md), [the hosted identity/scope contract](hosted-identity-scope.md), and [the PostgreSQL live-test guide](postgres-integration-tests.md). It narrows the decision to lock scope, authorization/revocation ordering, role boundaries, and provider prerequisites. It does not alter migrations 0001–0009.

## Threat model and control claims

| Threat | Confidentiality/integrity boundary | Availability and residual trust |
|---|---|---|
| Unauthenticated HTTP caller | Auth middleware must reject before project database selection or protected handler execution. | Request throttling is an edge/application control; not a lock control. |
| Authenticated principal without project access | Resolver checks principal status, workspace/project lifecycle, membership/grant, and action; project-login RLS is the database backstop. | Repeated denials can consume bounded request resources. |
| Query omits a tenant predicate | Forced RLS compares rows with the protected `session_user` mapping. | Intended source property only until live cross-scope reads/writes pass. |
| Project login holder can issue arbitrary SQL | The login mapping and RLS should continue to limit rows; a lock does not itself grant data access. | Current `PUBLIC EXECUTE` on advisory built-ins permits arbitrary lock keys. A holder can interfere with Celestin advisory locks across scopes. If the scoped wrapper is the only path, a project login can still hold its mapped **workspace** lock and delay workspace authorization changes. |
| Reader/admin credential or process compromise | Reader is a cross-workspace authorization-data identity; admin can mutate authorization facts. These are privileged control-plane trust boundaries, not tenant-content RLS boundaries. | Caller-selected reader/admin lock arguments can target unrelated workspaces/principals. Do not claim these credentials are contained against their compromise. |
| Central app process compromise or leakage of several project DSNs | A compromised process holding multiple configured project credentials can select another configured project. The per-login map does not contain that process compromise. | Potential cross-project access and outage; requires deployment/credential isolation beyond this lock design. |
| Database owner/provider administrator compromise | Database owners, superusers, `BYPASSRLS`, and provider operators can change policies, grants, roles, and function ownership. | Outside the application isolation boundary. |
| Long transaction, lock holder, or pool leak | No data disclosure follows from the lock alone. | Can stall same-workspace revocation, requests, or migration work. Statement timeout is not a total transaction/idle-transaction bound. |

### Security properties must stay separate

- **Confidentiality/integrity:** primarily depend on authenticated identity, final in-project authorization, protected `session_user` mapping, RLS, grants, and a trusted application/credential broker. Advisory locks are not authorization evidence.
- **Availability/interference resistance:** depends on who may invoke lock APIs, which identities can target which keys/rows, lock lifetime, pool limits, timeouts, and database boundaries.
- **Revocation ordering:** depends on every request and every supported mutation sharing a serialization mechanism and rechecking the authoritative facts before protected work.
- **Operations:** provider/DB owners, privileged preflight, migration execution, credential provisioning, and secret management are separate trust domains.

## Recommendation — conditional proposal, not approval

For the current shared-database architecture, the best-supported **conditional proposal** is to retain project `session_user` mapping and a narrow project request-lock wrapper, but only after:

1. Direct execution of every relevant advisory built-in is removed from `PUBLIC` and all request logins, and live tests prove the role profile.
2. The project wrapper derives/validates its target exclusively from `session_user`-bound mapping and has a reviewed owner/security profile. Its workspace-wide contention boundary is explicitly accepted.
3. The preliminary authorization-reader transaction becomes routing-only and does not take caller-targeted cross-workspace locks; the project transaction remains the authoritative reauthorization point.
4. Reader/admin lock wrappers remain unready until their global scope is removed or an explicit privileged-operation contract is approved. The admin credential is kept out of ordinary request handling.
5. Migration-runner lock/unlock and lock-function-owner privileges are separate profiles; the runner receives only its required session pair, while the reviewed function owner receives only the transaction primitives it calls.
6. A separate privileged preflight verifies the exact DB role, owner, full ACL/grantability roster, trigger/function catalog, and recovery readiness before operator use.

This proposal fits existing project-pool and RLS architecture and the current two-transaction route/final-authorization design. It is **not actionable on Neon yet** because the provider ACL, owner, and grantability operations are not evidenced. If those operations are unavailable, do not silently keep the same advisory design: choose and implement a complete row-lock redesign or database separation, and keep shared hosted mode disabled in the meantime.

No repository evidence justifies accepting the row-lock redesign without a new implementation and live race/deadlock proof. It is the principal provider-independent fallback to evaluate, not a ready substitute. A database-per-tenant architecture is a product/operations alternative, not a small fallback.

## Revocation ordering contract

### Existing documented behavior

`docs/hosted-identity-scope.md:25-29` and `docs/postgres-integration-tests.md:111-115` document this intended result: an authorized in-flight request that acquired the relevant shared lock first may finish; the revocation waits and commits afterward; requests that start after revocation commit are denied. The live race test `tests/postgres/test_live_authorization.py::test_inflight_authorized_operation_serializes_before_revocation` covers seven mutation classes in source, but no live test was run for this design task. This is an existing repository contract, not evidence of separate product-owner sign-off.

### Required advisory-lock sequence if the conditional proposal is approved

1. Authenticate the token before choosing a database identity. The workspace/project selector is input, not authority.
2. In a short read-only control transaction, resolve a candidate route. This result selects only a server-configured project pool; it does not authorize data access. Proposed change: do not acquire a global reader lock for this routing-only read.
3. Open the configured project login and begin the protected transaction. Apply bounded transaction-local settings.
4. Before reading authorization facts or protected rows, invoke the project wrapper. It verifies `session_user` against the protected mapping and takes the shared transaction lock for the mapped workspace. Then re-read principal status, workspace/project lifecycle, membership/grant, and action permission, bind the resolved scope, validate source references, and execute the protected operation in this same transaction.
5. Hold the shared lock through handler completion and commit. The transaction commit is the end of the protected request's authorization interval; commit/rollback releases the transaction lock.
6. A revocation transaction takes the matching exclusive lock before modifying status, membership/grant, lifecycle, or the login mapping. If the request owns the shared lock first, revocation waits; after request commit, revocation changes state and commits. Revocation takes effect at its commit.
7. If revocation owns the conflicting lock first, the request waits. After revocation commits, the request must perform its authoritative checks and deny before the handler. If its database isolation level cannot see/recheck the committed state after waiting, fail closed; do not continue using a stale route result.
8. On statement timeout, cancellation, disconnect, or handler failure, roll back and close/release the connection. Transaction locks must be released. Do not retry a protected write automatically after an uncertain commit; delivery/conversion replay policy is outside this lock decision and remains governed separately by D-08.

PostgreSQL wait/recheck semantics, role execution privileges, pool cleanup, and Neon behavior still require live testing. Current source configures `statement_timeout` but not a whole-transaction deadline, `lock_timeout`, or idle-transaction timeout. Product/SRE must set values from availability objectives; no values are approved here.

### Row-lock sequence if selected instead

1. The routing transaction remains a non-authoritative read and takes no tenant lock.
2. The project transaction locks every existing authorization fact row it relies on (identity, protected scope mapping, workspace/project lifecycle, membership, and the specific human/service grant) with a shared row lock, then rechecks them before the handler.
3. Every supported revocation/update path locks the same affected rows with a conflicting row lock before changing them. Writers and readers use a single reviewed table/primary-key order; multi-row administration cannot rely on planner order or an advisory trigger left from 0008/0009.
4. The request holds all authorization row locks through protected work and commit. A revoker that locks first commits before a waiting request rechecks; a request that locks first finishes before revocation commits. This preserves the documented in-flight policy only if the live tests prove every fact is covered and no deadlock or phantom path exists.
5. Replace or remove the 0008–0009 advisory triggers/wrappers in a forward migration only after every caller and writer has moved to the reviewed row-lock protocol. Replace the migration runner's advisory lock too if arbitrary project SQL must not interfere with migration availability.

The row-lock sequence is a proposal. Lock coverage, `SELECT ... FOR SHARE` permission under the configured role/RLS policies, concurrent writer ordering, and behavior after waits must be demonstrated on an approved disposable PostgreSQL target.

## Role and readiness boundaries

| Identity | Request/runtime responsibility | Privilege target and boundary |
|---|---|---|
| Project runtime login | One configured `(workspace_id, project_id)` pool; final authorization and content operation. | One protected mapping; no membership that permits `SET ROLE` to another tenant; forced RLS; minimum content DML. No direct advisory built-in execution in the ACL design. If scoped wrapper design is chosen, only the validated project wrapper. |
| Authorization reader | Read-only preliminary identity/workspace/project routing. | No tenant-content access. Proposed route-only path needs no advisory lock. This remains a trusted cross-workspace control-plane credential; do not expose its DSN to tool handlers. |
| Authorization administrator | Privileged provisioning/revocation only, outside request dispatch. | No ordinary MCP request pool. Keep readiness closed until lock targets and mutation scope have a database-verifiable or explicitly trusted control-plane contract. Do not expose arbitrary-key wrappers to project logins. |
| Migration executor | Explicit operator migration workflow only. | Separate DSN and exact DDL/ledger requirements. If advisory ACL design is used, needs only `pg_advisory_lock(bigint)` and `pg_advisory_unlock(bigint)` for the current runner. Never grant transaction wrappers' unrelated overloads merely because they share a function family. |
| Advisory-lock function owner (only if wrappers remain) | Own reviewed narrow security-definer functions/triggers. | Separate from request and migration identities where supported; no login, `BYPASSRLS`, role administration, or unrelated table authority. It needs only the exact transaction-lock overloads called. Fixed safe `search_path`, qualified references, constrained function body, explicit owner/grants. Current readiness instead insists the owner be database owner, so this must be reconciled before implementation. |
| Provider/database administrator | Provision roles/owners and perform provider-controlled ACL operations. | Separate operator identity, not present in hosted MCP process. Exact Neon capabilities and recovery authority remain unknown. |

**Request readiness** stays in `_assert_safe_hosted_pools` and checks only the authorization reader and configured project pools. It must not provision roles, run migrations, or silently use admin credentials. **Privileged preflight** is a separate operator command/workflow around `migrate_cli.main`/`apply_migrations` and the privileged provisioning composition. It must verify role identity/membership, exact effective and direct ACLs including `PUBLIC`, grantability/grantor, function/trigger owner and definitions, ledger state, migration serialization/recovery, and audit controls before any privileged operation. That workflow is not currently composed as a production operator tool.

## If Neon cannot change advisory-function ACLs

With the current shared-database advisory design, direct built-in lock calls remain an availability/serialization attack across workspaces. This does **not by itself bypass RLS or authorize a row read/write**, but it can delay requests/revocation and the migration runner. The exact hosted readiness validator rejects the present migration 0008–0009 profiles, so hosted readiness must remain false.

The no-ACL choices are:

1. **Redesign all Celestin request/revocation coordination around row locks**, remove every Celestin dependency on advisory locks, and replace the migration runner's session advisory lock with a protected migration-coordination primitive. Require a dedicated Celestin database (or inventory all other database consumers) so arbitrary advisory calls do not impact an unrelated application's locks. This is provider-independent but requires substantial code, grant, trigger, deadlock, and live-test work.
2. **Use a separate database per workspace or project.** Arbitrary advisory calls are then bounded to that database; per-project DBs isolate more tightly than per-workspace DBs. This still does not contain a central app process that holds multiple DSNs, protect a same-DB tenant, or make cross-database identity revocation atomic. It adds migration, provisioning, backup, monitoring, pooling, and reconciliation costs.
3. **Use a PostgreSQL host/configuration with verified ACL and ownership support.** This preserves the closest fit to the current architecture, but requires authoritative provider documentation or a successful guarded test on an explicitly approved disposable target. No such evidence is present here.

If none is selected, implemented, and verified against the agreed threat model, the safe fallback is: **hosted multi-tenant MCP remains disabled; local SQLite/stdio remains the supported path.** Do not relabel RLS as protection against arbitrary advisory-lock interference.

## Exact gates before migration 0010

Do not author 0010 until all applicable gates are met:

1. Product/security records the accepted threat model, whether workspace-wide lock contention is acceptable, the revocation-wins rule, and timeout/cancellation policy.
2. Database/provider owner supplies authoritative evidence for exact Neon/PostgreSQL version/role capabilities: inspect all supported advisory overload ACLs, revoke `PUBLIC` and request-role access, grant only required overloads, inspect grantor/grant-option/effective membership, create/retain the chosen function owner, and perform the intended operation in the migration/recovery boundary. A database name is not evidence.
3. Storage owner selects one lock architecture and records exactly which request and mutation paths participate. Reader routing and privileged admin writes have explicit scope semantics.
4. Reconcile readiness expectations with function security mode, owner identity, fixed safe `search_path`, schema qualification, triggers, grants, and separately verified role profiles. Do not tune readiness fixtures to migration SQL without security review.
5. Specify lock-key/serialization version and collision consequences if advisory locks remain; specify a non-advisory migration-coordination and fresh-bootstrap policy if they do not.
6. Define migration preflight, atomicity, rollback, and recovery. Keep all 0001–0009 files immutable. If an ACL action cannot be transactionally recovered, require an approved quiesced operator runbook before any use.
7. Run all relevant offline suites, then the guarded live PostgreSQL suite against an explicitly approved fresh disposable target using distinct migration, admin, reader, project A, and project B identities. Verify target identity before any migration.
8. Pass the live positive/negative tests in [the matrix](hosted-lock-isolation-test-matrix.md), including RLS, direct advisory calls, mapping, revocation races, lock release, rollback, timeouts, and migration serialization. Record a separate security/release approval before enabling hosted mode.

Until these gates pass, no live tenant-isolation claim is supported and hosted mode must remain disabled. D-08 delivery equality/replay semantics remain a separate contract and are not decided here.
